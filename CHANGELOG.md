## V6.9.3 - 2026-10-06
- Part A - low-fps interpolation at render time (a pre-step of the render input preparation; Valorant / CS2 detection, planner, effects, theme, song matching and settings untouched). Only the clips that are in the final plan are probed with ffprobe (avg_frame_rate, r_frame_rate, frames / duration for variable-frame-rate files); nothing is cached. A clip below 75% of the montage fps (30 fps clips in the 60 fps montage; 59.94 / 60 / 50 are not candidates) gets only the source ranges its takes use (+0.5 s each side) interpolated into a temporary `.mov` in `<output name>.interp\` next to the output, used as the take's input (the take's shift moves by the range start, so every kill time, beat, speed ramp and slow-mo stays where it was; interpolation happens before the retime); the folder is deleted after the render, also on failure or cancel. Non-candidates: the render command is byte-identical to V6.9.
  - Method (chosen on a generated pattern with moving text, a thin horizontal line, a moving thin line and a crosshair, against the true 60 fps frames): `minterpolate=fps=60:mi_mode=mci:mc_mode=obmc:me_mode=bidir:scd=fdiff:mb_size=8:search_param=8` (smallest block and search, no vsbmc, no large search range). SSIM of the intermediate frames: whole 0.998, moving text 0.989, thin lines / crosshair 0.999 (not warped); the blend-only variant (`framerate=fps=60`) ghosts moving text (0.86) and is used only if the motion method needs more than 4x real time on the PC (log line says so; about 25-30 s per source second at 1080p on a slow 4-core CPU, so expect that fallback on slow PCs).
  - Validation per segment (duration within one frame, exact frame count, decodes cleanly, mean SSIM against the source frames at their timestamps >= 0.90, no frame below 0.75 against its nearest source frame); any failure, ffmpeg error, more than 4x the segment's duration or a missing temp file: the original clip is used and one line "interpolation skipped: <clip> (<reason>)" is logged. The render never fails because of interpolation.
  - Log: "fps: N clips probed, K low-fps candidate(s) (<clip> 30 fps), I interpolated, F fell back", per segment "interpolated <clip> <start>-<end> s 30 -> 60 fps method=<m> in <t> s", "fps: N clips probed, 0 low-fps" when nothing is a candidate.
  - Hidden switch: config.json `"interpolate_low_fps": false` turns it off (default true, no UI setting).
  - New `python montage.py fpscheck [game] [--limit N] [--all]` (read-only ffprobe list of the newest dry plan's clips, or of all cached clips with --all; how many would be candidates; writes `fpscheck.txt`, never a cache).
  - New `test_v693.py` (generated clips; fps classes, 60 fps command / plan identical to V6.9, exact segment timing, cleanup, method SSIM, the four fallbacks, marker sync, switch, fpscheck, Valorant + CS2 guards).

## V6.9 - 2026-10-06
- CS2 neighbour-clip pairing at selection time (game == cs2 only; Valorant code path and the CS2 detection engine untouched - CLAUDE.md now says the CS2 engine is frozen). A fight recorded as a multikill can be split over 2-3 consecutive clips; the planner already merged / stitched continuation clips, but only among clips already in the selection. New step, after the selection (ticked clips, Random pick, weekly / Auto pick) and before the planner:
  - Clip time index (once per run, from file names and cached clip records only; no file reads, no decoding): sorted (start, end, clip), start parsed from the file name ("Counter-strike 2 2025.02.08 - 19.48.57.15.DVR.mp4", "Replay 2026-06-08 23-36-22.mov"; the `_1` / `_1_1` variants share the base time), end = start + cached duration. An unparsable name is skipped, never guessed.
  - For each selected CS2 clip that shows a kill within the first / last 3.0 s, or is a 1k whose kill is within 4 s of an edge, the previous and next clip are found by index. A neighbour qualifies only if its gap is at most 12 s (the planner's continuation test is inline in `build_events` and cannot be reused outside the selection, so the 12 s gap is used and the log says so), it has a cached kill entry (never scanned: "neighbour not scanned: <clip>"), it is not selected, not flagged used ("neighbour already used: <clip>") and has a kill of the player. Chain: at most 2 hops each way, at most 3 extra clips per selected clip, no clip twice.
  - Partners ("pair partner of <clip>") join the candidate pool; the planner's own merge / duplicate logic and frame-match stitch verification decide. A partner is only used when it is merged into the selected clip's event (more kills, containing all of its kills, no "stitch rejected"); otherwise the event stays exactly as before and the partner is dropped (never its own take, never flagged used - the flag is set from the rendered takes as before). Targets (length, number of clips) are not recomputed: a merged pair replaces the single clip's slot, other selected clips are untouched.
  - Zero-risk fallback: any error, missing cache or more than 2 s (the step runs in a helper thread with a hard 2 s cap) logs "pairing skipped: <reason>" and the original selection is kept. No settings, no caches or files written except the log lines.
  - Log: "pairing: checked N clips, M partner(s) added, S skipped (not scanned / used / no kills / no match)", "pair partner of <clip>: <partner> (gap 3.2 s)", and after the planner "pairing result: P pair(s) stitched, R rejected".
- New `python montage.py pairscan cs2 [--limit N]`: read-only list of the candidate pairs among all cached CS2 clips (gap, kills in each, why it qualifies or not; default the 30 with the most combined kills), written to `pairscan_cs2.txt`; changes no cache or flag.
- Note: the planner only merges two clips that share a victim (overlapping / duplicate captures); two consecutive clips with no shared kill stay separate events, so their partner is dropped. That planner rule is frozen and was not changed.
- New `test_v69.py` (generated clip lists and kills; about 10 s) with the Valorant guard against 031cb64 (100 generated clips: selection and plan identical).

## V6.8.2 - 2026-10-06
- CS2-only fixes in the red-border tracker, track merging, classification, kill list and rowdebug (Valorant, OCR, region storage / hashes, planner, effects, render, theme, song matching and settings untouched; existing sidecars in `montage_data\cs2_rows_v1` and the CS2 kill cache are NOT invalidated or rewritten: every rule is applied to the stored tracks at load time).
- Calibrated on the real killfeed screenshots (`tests\fixtures\cs2_rows`): the outline is a thin bright-red rectangle around the whole row (median BGR about (14-52, 30-54, 173-190), 1-3 px, row 21-25 px high at screenshot size) on rows where the player is the killer or the assister, never the victim (a death row has no outline). Colour thresholds are now R >= 80, R - max(G, B) >= 40, R >= 2.0 x max(G, B) (orange / brown backgrounds and yellow / orange team names no longer pass); lines of different length (a weak half line) and a merged line between touching rows are paired correctly; team colours are never used to identify the player.
- Row shape validation: an outline is a row only if it is a closed thin rectangle at least 4x wider than high with a valid row height, lasts at least 3 frames (or is still there at the end of the clip), ends at the right edge shared by the long-lived rows and sits on their row-slot grid. Everything else (bomb-site marker, map icons, explosions, red walls) is a non-row blob: never classified, never counted, not OCR'd in new sidecars; rowdebug prints "discarded N non-row blobs".
- Pre-clip: a track first seen within the first 0.6 s at full opacity (new sidecars store the outline strength at the first frame / its best) was already on screen and is not a kill; a row fading in is a kill. Sidecars built by V6.8.1 lack that value: for them a row first seen within 0.6 s on an older (not the newest) slot counts as pre-clip; rowdebug --all prints how many sidecars lack the data (rebuild with `bordercache cs2 --all`).
- Fragment merge: two tracks are ONE event unless they were visible at the same time in different slots or the first row had been gone for more than 1.0 s; they merge when they overlap in one slot, or the gap is at most 1.0 s and the victim texts match (CS2 normalisation / common core), or they were first seen within 0.35 s on one slot lineage, or they share the slot and outline width. No kills-per-round cap and no same-victim rule for border tracks (they stay in the name-based fallback only); rowdebug warns "possible Deathmatch/community server" for more than 6 distinct kills or repeated victims.
- Sides: another name first + '+' + the player = assist; otherwise a border track is a kill (player first with or without "+ mate", or an unreadable killer side). A border track is never a death: my name on its victim side is a suspicious misread (kept as a kill unless the killer side is a clearly readable other name; listed by rowdebug). A stable, clearly readable OTHER first name (4+ letters, same read in 3+ frames, similarity to every player name below 40) = other player's row, not a kill. Deaths and the 8 s lock keep coming from the existing name rule.
- rowdebug --all: one table sorted by suspicion (border vs name-based difference, 4+ kills within 2 s, 20+ discarded blobs, suspicious side reads, other-player rows), saved to rowdebug_cs2.txt.
- Cause of the "Valorant cache keys are identical" failure of test_v681 on the real PC: the test loaded the V6.8 baseline module with an EMPTY data folder, so the baseline used the default Valorant killfeed region while the current code read the calibrated `detect_valorant.json`; the two region hashes (and therefore the keys) differed. Not a code change: `test_v682.py` gives the baseline the same detect_*.json files.
- New `test_v682.py` (fixtures + generated rows + the Valorant guard against 031cb64, about 20 s) and `tests\fixtures\cs2_rows\` (kill_row, assist_row, death_row, kill_row_single; false_red_b_sign.png was not provided and is generated in the test).

## V6.8.1 - 2026-10-06
- Scope: CS2-only detection code (everything behind `game == "cs2"`), new helper functions, the Settings region picker, the Step 1 search bar, a new test file, version and changelog. Valorant detection and its cache keys, OCR itself, region storage and hashes, the planner's cut / beat logic, effects, render, theme, song matching and the other settings are untouched (the Valorant guard in `test_v681.py` compares the functions' source and the results with V6.8: 0 differences).
- CS2 red-border row tracking. In CS2 every killfeed row that involves the player has a red outline; other rows have none. New (no OCR): the killfeed region of a CS2 clip is decoded at 30 fps, outlined rows are found by colour (relative red thresholds, horizontal line pairs with red sides, tolerant of 1-3 px lines, 4:2:0 compression, fade-out and 1280x960 / 1024 sources stretched into the 1920x1080 space) and tracked by their outline width, text-independent appearance and position; when a new row pushes the list down the shift is measured from the rows that agree on it. A track survives 1.0 s without a detected outline; the same row back after more than 1.0 s is a NEW track. Tracks (first seen, last seen, slot over time, the OCR reads of their clearest frames) are written to a SEPARATE sidecar cache `montage_data\cs2_rows_v1\<clip>_<hash>.json` (valid for the same file, killfeed region, bar crop and tracker version). Existing kill-cache entries and keys are unchanged, so no rescan prompt appears.
- Classification (OCR on the clearest frames of each track only, up to 3 votes): the row is split at the weapon icon into killer / victim side and each side is compared with the player names with the existing CS2 OCR-confusion normalisation (plus the 火斧 recovery, also for a partly read '火茶' / '火年'). My name first on the left = KILL (a '+ assist' after it is fine); my name after a '+' with another name first = assist; my name on the right = death; small / square icon = utility. An outlined row with a weapon icon and no name match on the right = "kill (name unreadable, border confirmed)". Kill events = tracks classified as kill, time = the FIRST frame the track appeared, never rejected for a missing gunshot. A track is never counted twice; re-reads of one visible row with new spellings never create a kill; two rows of one victim are two kills only when the first row had been gone for more than 1 s. Pre-clip rows, deaths + the 8 s after a death, the more-than-5-kills-per-round cap and one-frame blips keep their rules. When a clip's sidecar exists the border-based list replaces the name-based list for CS2 (also in the clip list and in the planner); without a sidecar - or when a sidecar holds no outlined row at all - the V6.7.2 behaviour is used. Sidecars are built lazily when a CS2 clip's kills are computed (Dry plan / Render / Manual list after a scan) and right after a CS2 clip is scanned; one pass costs about 5 ms per decoded frame of tracking (decode time on top) plus about 1.5 s of OCR per outlined row on a slow CPU (the exact cost per clip is printed by bordercache / rowdebug).
- Cuts: no planner change. The planner now receives every kill row of the fight with its first-appearance time, so a take covers all of them (the existing 0.4 s row tail is measured from the LAST kill row, and a row already in the feed extends the take instead of being cut).
- New `python montage.py bordercache cs2 [--all]` (build the missing sidecars of the scanned CS2 clips; `--all` = every CS2 clip in the clip folders, existing sidecars rebuilt; prints the cost per clip) and `python montage.py rowdebug cs2 <clip name or path> [--all] [--rebuild]` (border tracks with first / last seen and slot, their classification with the OCR text of both sides, the old name-based kills and the difference; crops of each track at its clearest frame in `rowdebug_images\<clip>\row<n>_<time>.png`; `--all` prints one table sorted by the largest difference and saves `rowdebug_cs2.txt`; never writes the real kill cache or region files).
- Rescan only one region group (both games). Settings > Killfeed region: the button "Rescan this group to the current region" lists the clips that have an entry under the selected hash and none under the current region, asks "Rescan N clips from <hash> to the current region <hash>?" and on Yes scans only those clips under the current region and ADDS entries (old entries are never deleted or overwritten). Valorant: each old entry is first copied into `montage_data\valorant_cache_backup.json` (first copy per clip only); the question is the explicit confirmation. The progress bar shows it, the existing Cancel keeps the clips already scanned, it is refused while a scan or render runs, and it is disabled for the row that is the current region. `python montage.py rescanhash <game> <hash> [--confirm]` does the same; without `--confirm` it only prints the list and the count.

## V6.7.6 - 2026-10-06
- Killfeed region recovery and protection (detection rules, OCR, planner, effects, render, theme, song matching and settings untouched). Where it lives: `montage_data\detect_<game>.json` holds `{"region": [x0, y0, x1, y1]}` (fractions of the content rect; no key = the default region). The hash in every kill-cache key is `"ocr" + md5(repr(rounded region))[:8]`; the cache file name contains an md5 of the whole key, so a new region never overwrites or deletes the entries of the old one: stale entries (other hash) were only ignored ("0 scanned"), not deleted. The only deletions were "Rescan this clip" (`drop_file`, every hash of that one clip) and "Clear cache"; for Valorant "Rescan this clip" now replaces only the entry under the current hash (after a backup) and keeps the others. Each entry also stores the region it was scanned with.
- New `python montage.py regioncheck <game>`: current region + hash, default region + hash, the dated backups of the region file, and a table of the region hashes in the cached entries (entries, clips, earliest / latest scan date, the region the entries stored, which hash is the current one; others are marked STALE).
- New `python montage.py regionrestore <game> [--use <hash|default|backup:<file>|file:<path>>]`. It never picks a region itself and uses no majority rule: without `--use` it only lists the options with entry counts and dates and changes nothing. With `--use` it saves a dated backup of the current region file first, sets the region, checks that the result has the requested hash (else puts the old file back) and prints how many cached entries are valid and how many clips would need a rescan. A hash whose region values are not available (entries do not store it, no backup matches) changes nothing and says so.
- Stale Valorant entries are kept (marked stale in regioncheck) so regionrestore can make them valid again. A "calibration changed (killfeed region)" rescan of Valorant clips NEVER starts by itself any more: the scan skips them, logs how many and which hashes, and the GUI asks (once per set) "Rescan these N clips now?"; only Yes rescans them (CLI: `scan --confirm-region-rescan`). Before a cached Valorant entry is overwritten, the old entry is copied into `montage_data\valorant_cache_backup.json` (the first copy per clip is kept, the backup is never overwritten). CS2 behaves as before.
- Calibration dialog: the selected game is shown in large text (and follows the selection; opening a clip of the other game switches it, visibly), "Save this box as the <GAME> killfeed region?" must be confirmed before anything is saved, "Use default region" is now "Reset to default" (also asks first), and every save or reset first writes a dated backup `detect_<game>_backup_<date_time>.json`.
